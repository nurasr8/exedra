# Human-Like Code & UI Style Skill

## Назначение

Этот skill используется для того, чтобы код, комментарии, документация и UI не выглядели как шаблонный результат генеративного ИИ.

Цель — не намеренно делать код плохим или добавлять случайные ошибки, а избегать характерных для ИИ:
- чрезмерной идеальности;
- избыточной архитектуры;
- шаблонных комментариев;
- ненужной документации;
- однообразных именований;
- чрезмерно сложного UI;
- декоративных элементов без функциональной причины;
- повторяющихся паттернов генеративного ИИ.

Главный принцип:

> Пиши так, как писал бы опытный разработчик, который реально поддерживает этот проект, а не демонстрирует его в учебнике.

---

# 1. Общие правила

## 1.1. Не оптимизируй код под "идеальность"

Не следует автоматически:
- создавать дополнительные абстракции;
- разбивать простую функцию на несколько маленьких функций;
- создавать классы только ради организации;
- применять Design Patterns без необходимости;
- создавать интерфейсы и фабрики для единственной реализации;
- создавать отдельные конфигурационные слои для двух-трех значений.

Если простое решение работает и соответствует существующему проекту — используй его.

### Плохо

```python
class UserRepository:
    def get_user(self, user_id):
        return self._database.fetch_user(user_id)


class UserService:
    def __init__(self, repository):
        self.repository = repository

    def get_user(self, user_id):
        return self.repository.get_user(user_id)
```

Если между API и базой данных больше ничего не происходит, такая архитектура может быть лишней.

### Предпочтительно

```python
def get_user(user_id):
    return db.fetch_user(user_id)
```

---

# 2. Комментарии

## 2.1. Комментируй только то, что действительно требует объяснения

Не комментируй очевидный код.

### Не делать

```python
# Increment the counter by one
counter += 1

# Check whether the user exists
if user:
    ...
```

### Делать

```python
# The API sometimes returns an empty user object instead of 404.
if user:
    ...
```

Комментарий должен объяснять:
- почему код существует;
- почему выбран именно этот способ;
- неочевидное ограничение;
- workaround;
- поведение внешней системы;
- важное решение.

---

## 2.2. Не создавать комментарии ради количества

Не требуется, чтобы каждая функция имела комментарий.

Не добавляй docstring автоматически к каждой функции.

### Не делать

```python
def add_item(item):
    """
    Adds an item to the collection.

    Args:
        item: The item to add.

    Returns:
        None.
    """
    items.append(item)
```

### Предпочтительно

```python
def add_item(item):
    items.append(item)
```

Если функция действительно сложная:

```python
def rebuild_cache():
    """Rebuild the cache because the old format is incompatible with v2."""
    ...
```

---

# 3. Стиль комментариев

Комментарии должны соответствовать существующему проекту.

Не используй автоматически:
- академический стиль;
- чрезмерно формальный язык;
- пассивный залог;
- длинные объяснения;
- одинаковую структуру комментариев во всех файлах.

Не добавляй комментарии вроде:

```python
# Initialize the application state
# Configure the user interface
# Process the incoming request
# Return the resulting response
```

Такие комментарии ничего не добавляют.

---

# 4. Имена

## 4.1. Используй естественные имена

Имена должны быть понятными, но не обязательно максимально длинными.

Допустимы обычные сокращения, если они очевидны в контексте проекта:

```python
cfg
db
req
resp
ctx
tmp
idx
pos
img
btn
```

Не превращай каждую переменную в предложение:

```python
fetched_user_data_from_database
current_application_configuration_object
processed_image_with_detected_objects
```

Вместо этого:

```python
user
config
img
detections
```

---

## 4.2. Следуй существующему стилю проекта

Если проект уже использует:

```python
btn
img
cfg
```

не следует внезапно превращать всё в:

```python
submit_button
image
configuration
```

И наоборот.

Consistency внутри проекта важнее абстрактного "идеального" naming style.

---

# 5. Не добавляй искусственные ошибки

Не нужно специально:
- делать синтаксические ошибки;
- писать неправильные типы;
- использовать плохие имена;
- добавлять баги;
- ломать форматирование;
- удалять необходимые проверки.

"Человеческий код" ≠ "плохой код".

Цель — убрать характерные признаки генерации, а не ухудшить качество.

---

# 6. Архитектура

## 6.1. Сначала простое решение

Перед созданием новой абстракции спроси:

> Можно ли решить это существующим кодом без добавления нового слоя?

Если да — не добавляй слой.

Не создавай автоматически:

```text
Controller
Service
Repository
Manager
Factory
Provider
Adapter
Strategy
Handler
Builder
```

только потому, что это "правильная архитектура".

---

## 6.2. Не использовать SOLID механически

SOLID — инструмент, а не обязательный шаблон каждого проекта.

Не создавай Dependency Injection, интерфейсы или несколько классов, если проект от этого не выигрывает.

---

# 7. Мертвый код

Не оставляй код только потому, что он выглядит полезным.

Удаляй:
- неиспользуемые функции;
- неиспользуемые переменные;
- недостижимые ветки;
- повторяющиеся реализации;
- старые альтернативы;
- закомментированный старый код.

### Не делать

```python
# old implementation
# def process(data):
#     ...
```

Если старый код больше не нужен — удалить его.

---

# 8. Защита от "AI hallucination"

Перед использованием API, библиотеки или метода:

1. Проверь, существует ли он.
2. Проверь его актуальное название.
3. Проверь версию библиотеки проекта.
4. Учитывай уже существующие зависимости.

Никогда не придумывай API по аналогии с другой библиотекой.

### Плохо

```python
widget.setModernTheme(...)
```

если такой метод не существует.

Если API неизвестен — сначала проверь документацию или исходники проекта.

---

# 9. Не добавляй лишние зависимости

Не добавляй библиотеку для задачи, которая решается стандартной библиотекой или существующим кодом.

Особенно избегай добавления:
- utility packages;
- wrapper libraries;
- UI frameworks;
- небольших helper packages

только ради одной простой операции.

---

# 10. Версии и актуальность

Не копируй решения только потому, что они были распространены раньше.

Перед использованием:
- deprecated API;
- старых методов;
- устаревших библиотек;
- старых конфигурационных форматов

проверь текущую версию проекта.

Если проект намеренно использует старый API — не обновляй его без причины.

---

# 11. Не переписывай существующий код без необходимости

Если требуется добавить одну функцию, не переписывай весь файл.

Сохраняй:
- существующий стиль;
- структуру;
- имена;
- форматирование;
- архитектуру.

Изменяй только необходимое.

---

# 12. UI: основной принцип

UI должен выглядеть как настоящий рабочий инструмент, а не концепт из Dribbble.

Приоритет:

1. функциональность;
2. читаемость;
3. навигация;
4. доступность;
5. согласованность;
6. эстетика.

Не наоборот.

---

# 13. Не злоупотребляй визуальными трендами

Не используй без причины:
- glassmorphism;
- neon glow;
- gradients;
- backdrop blur;
- огромные скругления;
- floating cards;
- 3D-иллюстрации;
- декоративные blobs;
- excessive shadows;
- glowing borders.

Если элемент не помогает пользователю — его существование должно быть обосновано.

---

# 14. Цвета

Не используй автоматически типичную AI-палитру:

```text
#6366F1
#8B5CF6
#EC4899
#06B6D4
```

и похожие сочетания только потому, что они выглядят "современно".

Цвета должны соответствовать:
- платформе;
- существующей теме;
- бренду;
- назначению приложения;
- accessibility требованиям.

Если проект KDE — придерживайся визуальных принципов KDE.

Если проект GTK — придерживайся GTK/GNOME conventions.

---

# 15. UI-компоненты

Не превращай каждую часть интерфейса в отдельную карточку.

Плохо:

```text
┌─────────────────────────┐
│      Card               │
│                         │
│   ┌─────────────────┐   │
│   │ Another Card    │   │
│   │                 │   │
│   └─────────────────┘   │
│                         │
└─────────────────────────┘
```

Используй обычные:
- списки;
- панели;
- toolbar;
- tabs;
- dialogs;
- forms;
- buttons;
- menus.

там, где они подходят.

---

# 16. Размеры и spacing

Не используй случайный набор:

```text
13px
17px
23px
31px
37px
```

Если проект использует систему размеров — придерживайся её.

Не добавляй огромные пустые пространства только ради "воздушности".

---

# 17. Состояния UI

Для интерактивных элементов учитывай реальные состояния:

- normal;
- hover;
- pressed;
- checked;
- disabled;
- focused;
- selected;
- loading;
- error.

Не создавай дизайн только для красивого статичного screenshot.

---

# 18. Иконки

Используй существующую icon system платформы, если она есть.

Не рисуй сложную SVG-иконку вручную, если подходящая системная иконка уже существует.

Особенно избегай случайных декоративных SVG.

---

# 19. Адаптивность

Не подгоняй интерфейс под один screenshot.

Проверь:
- маленькое окно;
- большое окно;
- длинный текст;
- масштабирование;
- системный шрифт;
- разные DPI;
- отсутствие некоторых элементов.

UI не должен ломаться при небольшом изменении размера.

---

# 20. Текст интерфейса

Используй нормальные короткие названия.

### Плохо

```text
Initialize New Project Workspace
```

### Лучше

```text
New Project
```

Не используй маркетинговый текст там, где достаточно обычной подписи.

---

# 21. Не добавляй декоративный AI-контент

Не создавай без необходимости:

```text
Welcome back, developer! 🚀
Build something amazing today.
```

или:

```text
Your creative coding journey starts here.
```

Рабочие приложения обычно не нуждаются в таком тексте.

---

# 22. Код и UI должны соответствовать друг другу

Если проект простой — UI и архитектура тоже могут быть простыми.

Если существующий проект написан небольшим количеством классов, не превращай его внезапно в enterprise architecture.

Если проект использует KDE conventions — следуй KDE conventions.

Если проект использует обычный Python — не вводи сложную архитектуру только ради демонстрации паттернов.

---

# 23. Перед завершением работы

Перед выдачей результата проверь:

## Код

- [ ] Нет придуманных API.
- [ ] Нет лишних зависимостей.
- [ ] Нет мертвого кода.
- [ ] Нет ненужных абстракций.
- [ ] Имена соответствуют существующему проекту.
- [ ] Комментарии объясняют только неочевидные вещи.
- [ ] Нет автоматически сгенерированных docstring для простых функций.
- [ ] Код не переписан без необходимости.
- [ ] Используемые API соответствуют версии проекта.

## UI

- [ ] Нет декоративных элементов без функции.
- [ ] Нет чрезмерного glassmorphism.
- [ ] Нет случайных градиентов.
- [ ] Нет типичной "AI cyberpunk" палитры без причины.
- [ ] Используются системные компоненты там, где это возможно.
- [ ] Есть нормальные состояния интерактивных элементов.
- [ ] Интерфейс работает при разных размерах окна.
- [ ] Текст читаемый и практичный.
- [ ] Иконки выглядят нормально.
- [ ] UI соответствует платформе.

---

# 24. Главный принцип

Не пытайся "выглядеть человеком".

Вместо этого:

> Понимай существующий проект, его ограничения и стиль, а затем делай минимально необходимое изменение естественным для этого проекта способом.

Избегай как стерильного "идеального AI-кода", так и намеренно плохого "человеческого" кода.

Код должен выглядеть как продолжение уже существующего проекта.
